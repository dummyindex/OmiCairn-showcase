How it works

How OmiCairn works

OmiCairn plans an analysis, runs the code, and then checks its own work at three layers before it reports anything. When a check fails, the run goes back and redoes the step. Every check leaves a record, so each claim can be traced to the code that produced it.

Overview

Two levels, one memory

OmiCairn works at two nested levels. Both use the same model backbone, the same containerized execution and the same experience store. Inside a task, repair, review and verification loops correct the work. Across tasks, experience replay carries lessons forward.

Node level

An analysis tree

One analysis request becomes a tree of small, executable steps. Each step is planned, run in a container, repaired if it fails and reviewed before anything is built on it.

Used for the case studies and the benchmark.

Run level

A verification-gated research run

A hypothesis-driven run moves through eight phases. Four produce work and four check it. A run continues only when the current phase passes its gate.

Used for the neurodegeneration campaign.

Across tasks

Experience replay

Fixes, review findings, pitfalls and expert directives are stored as experience items. Confirmed items are shown to later agents as advice. The model itself never changes.

How items are promoted

Node level

An analysis tree that repairs and reviews itself

Each analysis is stored as a tree. The root registers the input data without changing it. Every other node is one analytical step that reads the outputs of its parent. The tree records the code, parameters, logs, inputs, outputs and review decisions of every step, including the attempts that failed.

What a step is

Each step is a function block: Python, R or shell code with a manifest of its inputs, outputs and parameters and a list of software requirements. All blocks share one entry point, so any block can be run, rerun or swapped the same way. The FunctionCreator agent first looks for a validated block in the library and adapts it; only if none fits does it write a new one. A separate check reads the code before it runs.

What review looks at

Code first collects evidence from the step: how many output files and figures it produced, how large they are, how many warnings the logs contain, whether the logs show real computation on the input, and whether outputs contain placeholder markers such as “mock”, “dummy” or “example data”. The Reviewer agent then judges the step against its task. It names concerns by type:

  • Cheating: results not derived from the input data, such as hard-coded or simulated values reported as findings.
  • Placeholder: stub outputs.
  • ML-practice violation: improper data splitting, information leakage or missing validation.
  • Implementation mismatch: the code does not do what the step says.

A request to redo the step, or a critical concern of one of these types, blocks the step. Smaller concerns are passed to the Orchestrator without stopping the analysis.

Changing a step

If a user edits a step, changes its parameters or asks for a rerun, only that step and the steps that depend on it are recomputed. All other outputs and all earlier execution records are kept.

The agents

MainAgent
A deterministic controller. It runs the session, creates re-attempts and calls the other agents. It uses the model only to interpret the request.
Orchestrator
Decides whether the request is satisfied and, if not, plans the next steps from the tree, the failures so far and curated domain knowledge.
FunctionCreator
Reuses a validated function block or writes a new one for each planned step.
BugFixer
Repairs a failing step in a bounded session: it reads logs and files, edits code, installs packages and runs diagnostics.
Reviewer
Judges whether a step that ran is an adequate analysis, using the evidence code collected.
WebAgent
Retrieves software documentation, code repositories, biological databases and, when enabled, scientific literature.

Every agent must return output in a fixed schema. Attempts, repairs, branches and the size of the tree are all bounded, so a session always ends.

Run level

Eight phases, four of which check

A research run starts from a written question. It moves through eight phases in order. Every phase except CROSS-CHECK is carried out by a model-based agent; CROSS-CHECK is plain code. When a checking phase finds a problem, it sends the run back to the phase that can fix it.

Going back is part of the design

Each phase may only make the decisions allowed for it; any other decision is rejected and the phase runs again. Every route back is counted. Each phase can run only a limited number of times, and a run can only go back a limited number of times. A run that would exceed either limit halts instead of looping.

Each pass through a phase writes to a new directory that is never overwritten. Later phases can read earlier work but cannot change it; an edited report is saved as a new file. This is what makes a run auditable after the fact.

Runs can also stop for reasons outside this logic, such as an infrastructure failure or an exhausted usage quota. In the campaign, 17 of 41 genuine runs reached multi-agent review. Halted runs and their hypotheses are published too.

A run can also be started in ideation mode, in which it only proposes research directions and ends before SCOPE.

Accountability

Three layers of checking

The layers look at different things. Code checks that the numbers are internally valid. A claim-review agent checks that every sentence of the report is backed by those numbers. Reviewer agents judge whether the analysis answers the question. A failure at any layer sends the run back.

Layer 1 · CROSS-CHECK

Deterministic gates

Run by code alone, without a language model.

  • Every confidence interval is finite and ordered, and every estimate lies inside its interval.
  • Bounded metrics, such as AUC, correlations and P values, lie in their allowed ranges.
  • A comparison with a baseline on the same samples reports the paired difference and its interval.
  • Intervals quoted in the notes are identical to those in the results file.
  • The headline comparison was produced by the code that ran in this stage, not recovered from a failed stage or typed in by hand, and is not degenerate.
  • No hypothesis is called supported unless its decision rule was met.
  • The pre-registration has not changed since PLAN.

Further gates only warn: whether the minimum detectable effect is reported, whether declared figures exist, whether software lock files are present, and whether multiple comparisons are corrected.

Any error sends the run back to EXECUTE.

Layer 2 · CLAIM-AUDIT

Claim-review agent

Reads the report one sentence at a time.

Each sentence is classified (quantitative, qualitative or methodological claim, narrative, definition, prediction or filler) and labelled supported, partially supported, unsupported, over-claimed, under-claimed, filler or style. Claims need evidence of the right kind:

  • A number must cite an entry in the results file, and the stored value, rounded as quoted, must match.
  • A qualitative claim must cite a publication from the run’s literature set.
  • A methodological claim must cite a file or a field of the pre-registration.

The agent then edits the report using existing results only: filler is removed, over-claims are softened, under-claims strengthened. A sentence it cannot fix stays in the report and is flagged for human revision. Code then verifies the audit ledger, and every reference must resolve in Crossref or PubMed.

Unsupported or excess over-claimed sentences send the report back to REPORT.

Layer 3 · REVIEW and PANEL-REVIEW

Reviewer agents

Separate from the agents that did the analysis.

An internal reviewer agent receives the audited report, the results, the audit ledger and the cross-check warnings. It scores eleven dimensions: novelty, methodological rigor, statistical validity, domain depth, figure quality, clarity, references, honest limitations, reproducibility, anti-fabrication and comprehensiveness. Each over-claim left after the audit costs anti-fabrication points.

Its decision names the cause: weak analysis goes back to EXECUTE, weak presentation to REPORT, a flawed design to PLAN, a question that contradicts the data to SCOPE. A run that cannot be saved halts.

A panel of three reviewer agents follows: a domain expert, a methodologist or statistician, and a reproducibility advocate. They do not see each other’s assessments.

The run ends as done only if all three accept. These are agents inside the system, not human peer reviewers. On the campaign pages, “completed the pipeline” means reached this review, not accepted by it.

Pre-registration

The rule is fixed before the analysis runs

In PLAN, every hypothesis gets a decision rule. The rule is stored with a cryptographic hash. EXECUTE and CROSS-CHECK recompute the hash; any change is reported as pre-registration drift and blocks the run. A hypothesis can be called supported only if its rule is met.

Anatomy of a decision rule

Metric

What is estimated, for example a donor-level AUC or an effect size.

Direction

At least, more than, at most or less than.

Threshold

The value the estimate must reach, written down in PLAN.

Null value (optional)

A value, such as chance level, that the 95% confidence interval must exclude.

The rule is met only if the estimate passes the threshold in the stated direction and, when a null value is given, the interval excludes it.

Which comparisons matter

The pre-registration also names one headline comparison, the load-bearing comparisons on which a verdict depends, and the discriminating comparisons that separate competing explanations. CROSS-CHECK fails the run if any of them is missing.

Verdicts need an evidence path

Each run keeps a knowledge graph of hypotheses, findings, datasets and publications. A hypothesis can be marked supported, partially supported or refuted only through a finding whose evidence path points to a non-empty file that a pipeline stage produced.

Can the data answer the question?

At the end of SCOPE, and again at the end of PLAN, the agent rates the match between question and data as feasible, underpowered or needing data. Missing data send the run back to SCOPE to revise the question or the sources; an underpowered design sends PLAN back to change the design, for example to pooled cohorts.

How verdicts appear on this site

Every hypothesis of the campaign carries one of these outcomes. The first five count as evaluated.

Expert in the loop

Humans stay in the loop

OmiCairn is built to be steered by computational biologists, not to replace them. Experts act at four points:

  • Notes. An expert can attach a note to a phase. The agents must treat it as authoritative.
  • Steering. An expert can reopen a specific phase. A reopened phase counts toward the same limits as any other route back.
  • Flagged sentences. Sentences the claim-review agent cannot fix are left in the report and flagged for human revision.
  • Experience. An expert confirms, edits or rejects experience items that are not promoted automatically, and expert directives are stored as experience for later runs.

Across tasks

Experience replay: learning without changing the model

Every task leaves feedback behind: errors and the repairs that fixed them, review concerns and the revisions that cleared them, audit failures, reviewer comments and expert notes. OmiCairn keeps this feedback as structured experience and shows it to later agents. What an agent is shown changes; the model, its instructions, the review criteria and the gate thresholds do not.

Collection

After each task or run, a reflection agent reads the record and proposes candidate items. Each item stores the situation that triggered it, the reusable content, the agents and phases it applies to, links to its source, and how it was verified. A candidate that repeats an existing item is merged into it, and the item’s count of independent observations goes up.

Confidence-gated promotion

Confidence is highest for items confirmed by an observed outcome and seen repeatedly, for example a fix after which the code ran, or a revision after which a step passed review. It is lowest for items that rest only on an agent’s interpretation.

  • Expert directives become active directly.
  • Outcome-verified items with enough confidence that do not conflict with an active item become active automatically.
  • Everything else waits for a human computational biologist, who accepts, edits or rejects it. Until then it is never shown to an agent.

Rejected items are kept with the reason, so the same proposal is not raised again. When an expert activates an item that conflicts with an older one, the older item is retired.

Replay

When an agent acts, it is shown the active items that apply to its role and phase, ranked by similarity to its current situation: debugging fixes to the BugFixer, function blocks to the FunctionCreator, pitfalls and practices to the planning, coding and phase agents. Each item is shown with its class and confidence, as advice rather than a rule. Every replay is logged, so a later output can be traced to the experience that shaped it.

Starting from an empty store, OmiCairn accumulated about 439 items over the work reported in the manuscript, spanning reusable analysis skills, experiences and policies. How much the full store, and expert confirmation, improve later work has not yet been measured.

Limits

What these checks do not guarantee

  • Consistency is not truth. The checks verify that numbers, sentences and verdicts trace back to code that ran on the stated data. They cannot show that the biology is right.
  • Reviewer agents are part of the system. Their review is not human peer review. In the manuscript, two external domain reviewers scored seven campaign reports lower than the internal reviewer did.
  • Completing the pipeline is not validation. A run that reached review passed through every phase; it was not thereby shown to be correct.
  • Many tests were weak. Many executed analyses were underpowered, used fallback tissues or surrogate methods, or could not reach the intended data. The adjudication note of each hypothesis says so.
  • Flagged problems were left in place. Sentences flagged for human revision remain in the delivered reports.
